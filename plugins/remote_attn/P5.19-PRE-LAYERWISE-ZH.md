正式接入、发布制品、接流量前预热、容量预算、灰度与回退使用 [生产接入手册](DEPLOYMENT-ZH.md)；本文保留实现与实验细节。

的 `a57f4613803fd099a3a90a2defafcb01d17bd57c`：复用 split-prefill，层组计算结束后记录 CUDA event，传输线程等待 event 后发送该组 K/V。
没有整体 cherry-pick 上游 PR，也没有移植其中 hybrid / speculative 支持。
CPU 合约测试不代表 GPU 正确性或性能验收；当前尚无这版的 CUDA E2E 性能结论。

## 接入位置与所有权

- `sglang_remote_attn/pre_layerwise.py`：Scheduler 实例持有控制器；负责最终 chunk 的层组计划、提前准入、TP 一致回收和 journal。
- `handoff_control.py`：复用 RemoteHub、epoch、RPC 引用租约和已有的 attention wrapper；新增可选 release 回调，让原生 PD 保留 KV 分配的最终所有权。
- `hooks.py`：薄封装 `run_batch`、`ModelRunner.forward`、`send_kv_chunk`、`pop_transferred` 和 idle 判断；不复制调度循环。
- Mooncake：可选 `kv_buffer_indices` 只选相同布局的指针；`on_complete` 在全部目的端写成功后执行。失败、取消、目的范围不足均不能发布层完成证明。
- Decode：`_commit_transfer_to_req(..., keep_receiver=True)` 提前使用首 token 元数据，但保留 receiver 和 metadata slot 到真实传输完成。

P 在最终 chunk 开始计算前为整段尾部索引预留一次发送区间。每个层组结束即提交指定 K/V buffer 的任务。P 完成采样后，独立发送首 token 元数据并发布 Remote 服务地址；随后仍向同一原生 FIFO 提交最终 metadata 任务。**没有提前伪造 `KVPoll.Success`。**

D 收到匹配 generation 的 ready 标记、确认本地 metadata 的 bootstrap room 正确，并在全部 TP rank 同意后，使用已有的原生 Req 开始 decode。已完成层走本地 attention，其余层用 P 的前缀加 D 的本地 tail 做 Remote Attention。P 的 HTTP 侧使用一次性的 response snapshot 提前结束，活的 Req 继续等待真实传输完成，避免 router 等到全部 KV 传完才转发 D 的结果。

P 的 KV 释放需同时满足：原生发送结束、D 已退出 Remote、在途 RPC 读引用归零；实际释放在 TP 全体确认后进行。D 在原生传输成功前不清 receiver、不归还 metadata slot。取消时先 drain；超时或无法证明写入结束则报错并保留分配，首版没有在线恢复协议。pending lease 会阻止 idle cache reset。

## 沿用部署时的 token 分块

token chunk 大小完全由模型部署和原生调度器决定；启用 pre-layerwise 不需要另设 chunk size，也不改写部署参数。插件直接读取本轮请求的实际 `extend_len`，因此会自然跟随动态分块、不足整块的尾块和不启用 token 分块的部署。`HANDOFF_PRE_LAYERWISE_GROUP_SIZE` 只控制层分组，不控制 token 分块。

- 中间 token chunk 沿用原生整层发送。
- **只有最终 token chunk 按层组流水发送**，包括不足 chunk size 的尾块。
- 同 room 的原生任务使用同一 FIFO；最终 chunk 的某层组写入完成时，前面的普通 chunk 已结束。因此该层的证明覆盖完整前缀 `[0, prompt_len)`。
- 不把“某层发送已提交”当作“完整前缀已经可读”，不重复发送整个最终 chunk。
- batch 中含中间 chunk 时仍可执行 split-prefill，但只为合格的最终 chunk 提交层组发送；有 embedding override / hidden-state capture 的 batch 沿用普通路径。

中间 chunk 的提交不代表传输已经完全隐藏，仍须观察积压。默认层分组采用 #34905 的启发式：TP 一致接受的最终 chunk 总计算 token 数不足 3072 时不做跨层流水；否则按实际 batch 平均 `extend_len` 将目标组数从约 10 组逐步减至约 4 组，达到 9216 tokens 后保持约 4 组。36 层模型的大 chunk 因此每组 9 层。该策略不是测量带宽的在线调优。

小尾块（或模型不超过 4 层）在 `layerwise` 模式走原生路径，在 `remote` 模式保留提前解码、将全部层合成一次发送；后者不声称有跨层计算/传输重叠。正数 group size 仍可用于显式覆盖层分组做对照，但日常运行无需设置。

## 开关与运行

两端安装本工作树的 SGLang 和插件。原有插件仍需 `SGLANG_PLUGINS=remote_attn`、各角色独立的 `HANDOFF_CTL_DIR`。
模式、共享目录和层组策略在 P/D 一致设置；发送 staging 由 P 控制，接收 staging 由 D 的 offer 协商，两端都需升级到本版本：

| 变量 | 默认值 | 含义 |
| --- | --- | --- |
| `HANDOFF_PRE_LAYERWISE` | `off` | `off` 保留原路径；`layerwise` 边算边传但等待完整 KV；`remote` 启用提前准入与 Remote |
| `HANDOFF_PD_DIR` | 无 | P/D 可见的同一个本机绝对目录，按 room/rank/generation 隔离 |
| `HANDOFF_PRE_LAYERWISE_GROUP_SIZE` | `0` | 自动选择层组；正数固定每组层数，尾组可不足该值；不修改 token chunk |
| `HANDOFF_PRE_LAYERWISE_HOST_STAGING` | `MC_FORCE_TCP=1` 时为 `1`，否则为 `0` | 仅层组发送使用专用 stream 的 pinned-host staging；`0` 用于原 GPU 指针路径对照 |
| `SGLANG_DISAGG_STAGING_BUFFER` | `0` | P/D 同时开启，层组复用原生 ring、STAGING_REQ/RSP、CHUNK_READY 和 watermark；普通同 TP token chunks 仍走原路径 |
| `HANDOFF_PRE_LAYERWISE_RECV_HOST_STAGING` | `0` | 仅 D 控制 ring 的存储：`0` 为 GPU ring，`1` 为 pinned host ring＋GPU shadow；需要开启原生 staging |
| `SGLANG_DISAGG_STAGING_POOL_SIZE_MB` | `4096` | 每个 D rank 的 ring 容量；host 模式另保留等容量 GPU shadow，必须容得下最大层组 |
| `HANDOFF_PD_DRAIN_TIMEOUT_S` | `300` | 活跃源租约与清理等待上限；不能小于实际长请求耗时 |
| `HANDOFF_PL_RETIRE` | `async` | P 层组任务由 daemon reaper 延迟释放；`off` 和 `keep64` 是诊断对照 |
| D2H 冷态预热 | 自动执行，无独立开关 | 发送 slot 新注册或扩容后在同一 stream/buffer 上做一次 最多 16 MiB真实 D2H；复用不重复 |

当前范围：Qwen3ForCausalLM、dense NHD MHA BF16/FP16、CUDA、相同 TP 宽度、PP=DP=CP=1、page size 1、关闭 radix cache / overlap scheduler，Mooncake 同布局单目的端、early allocation。CUDA graphs 可沿用原生配置：Remote/逐层等待时全 TP eager，全部 Local 且原生 graph 条件满足后恢复 replay；最终分层 prefill 仍 eager。LoRA、embedding override 的流水路径、KV checksum、原生 host KV destination、HiCache、统一 KV、PD multiplexing、speculative 不支持。开关不匹配或 offer 尚未就绪的请求走原生路径，必须检查实际 activation 数量。

这是同机共享目录控制协议；KV 仍走原生 Mooncake。不能直接用于跨机部署。逐层完成在调度步之间刷新，本路径禁用按 RPC 耗时切换为阻塞 layer-wait；后续可增加异步通知优化。不要同时向这些 Req 发 P5.18 freeze/migrate 控制命令。

### TCP 发送端 staging

现场实验定位到 Mooncake TCP 的 GPU 指针发送使用无 stream 参数的同步拷贝，可能被同进程 Prefill 的默认流阻塞。层组路径现在可在发送前使用 `cudaStreamNonBlocking` 私有流，把原生地址计划中的各段 D2H 到已注册的 pinned host buffer，再经原来的 `_transfer_data` 发送 host 地址。copy stream 等待该层组的 ready event，完成自身 event 后才提交 TE；不使用全设备同步。

- 每个 P rank 持有独立的 stream 和可复用 buffer；首次分配、扩容及注册发生在该轮 Prefill 前。
- 原生 KV 索引顺序、目标地址、字节数、分批上限、Send Lock、pre-send probe 和 session 均保留；发送 Batch 沿用部署配置，不要求为 8，也不要求与 token chunk 相等。只有带层组 subset 的任务携带 staging adapter，普通 PD、中间 token chunk 和 Post-Remote 仍走原路径。
- 容量按本轮最大层组和原生实际 batch 上限预留；同一 buffer 的 D2H 与 TE 发送串行占用，只有成功返回后才复用。扩容先安全注销旧 buffer，正常 shutdown 在请求 drain 后注销并释放。
- 注册、拷贝、传输或注销失败会隔离该 slot，保留 engine 对存储的强引用，阻止复用及源 KV 释放；不把超时当成完成，不回退重发 GPU 地址。该失败路径需要停止进程处置。
- 发送 staging 本身不改变接收端 GPU 指针路径。接收端私有流需单独开启下述开关。

`SGLANG_MOONCAKE_MAX_TRANSFER_BATCH_INDICES` 的原生默认是 `0`（不按此上限拆分），参考启动脚本未配置时使用 `2048`，已有外部配置优先。更换启动入口时核对有效值；更大 batch 可能增加 P staging 容量，不能把调整 batch 的收益混入 staging 对照。

`prefill.json`、汇总 report 和 activation 日志记录是否启用了 `host_staging`。发送端 D2H adapter 独立保留；接收端可启用下述原生 staging ring。

可在部署环境运行实际 Mooncake TCP 的双 GPU 复现程序（需要安装 `cuda-python`，SGLang 已声明该依赖）：

```bash
python test/manual/remote_attn/pre_layerwise_staging_probe.py \
  --source-device 0 --destination-device 2
```

程序比较 GPU 指针/host staging 各自的空闲与默认流繁忙场景，逐 buffer 校验全部字节，并检查 staging 是否在模拟计算结束前完成。繁忙场景使用 CUDA sleep 隔离流依赖，不代表真实模型的 HBM 压力；该程序不会修改模型部署的 chunk 配置，也不能替代真实 P/D 的 TP2 输出一致性和 TTFT/E2E 验收。

### 层组 Event 延迟回收与 D2H 冷态预热

发送完成后销毁 `transfer_fn=partial(..., ready_event=event)` 可能释放 Event 的最后引用，并在传输 worker 上触发昂贵析构。现在 `async` 将处理完的层组任务引用移交 daemon reaper，入队前先转移 worker 的所有权，避免消费者抢先回收后最后引用仍落在 worker 的竞态。等待原生 watermark 而重入队的任务不提前退休，完成证明仍由原有发送/接收路径决定。

每个 worker 有 64 槽待回收队列，另有 1 个正在回收；正常使用 `put_nowait`，满载会记录 `Layer-group reference reaper full; waiting for capacity` 并背压等待。满则直接丢引用仍可能在 worker 析构，因此不能保证任意积压下绝不阻塞。`HANDOFF_PL_RETIRE=off` 为 inline 释放对照，`keep64` 保留最近 64 个任务但淘汰/退出仍可能阻塞，仅用于诊断。

core 共享 slot 的 `reserve()` 注册新 slot 后，在同一私有非阻塞流把最多 16 MiB scratch 数据 复制到同一已注册 pinned host buffer，并等拷贝完成；随后才进入层组 Prefill。扩容重复此步骤，复用不重复；预热异常只有在确认 copy stream 已排空后才告警继续，否则 quarantine。

最多 16 MiB预热针对首次拷贝初始化，不是整段内存或完整网络/模型预热。首次 slot 在首个请求内创建时，预热成本仍属于该请求；`preflight` 和 `/health` 也不能替代业务路径预热。生产上线应在导流前经 router 发送覆盖实际分块/容量的请求，检查所有目标 rank 的 staging 激活与回收，冷态首请求和热态性能分开统计。没有新的 warmup 环境变量，也没有更改 token chunk。

### TCP 接收端：复用原生 staging ring

两端设置 `SGLANG_DISAGG_STAGING_BUFFER=1`，D 设置 `HANDOFF_PRE_LAYERWISE_RECV_HOST_STAGING=1`。D 在启动时注册 pinned host ring，原生 `staging_base_ptr` 握手直接公布该地址。`HANDOFF_PRE_LAYERWISE_RECV_HOST_STAGING=0` 保持原生 GPU ring，作为相同协议的对照；原生 staging 关闭时保留此前直接写 KV pool 的路径。两端需使用本分支的新版本。

```text
原生 STAGING_REQ/RSP：为最终 token chunk 的各层组分配 ring 区间
KV ready → [P 私有流 D2H（可选）] → TE 分批写 ring 对应偏移
         → 原生 CHUNK_READY
         → 已有 _scatter_stream：host ring H2D → GPU shadow → 原有 scatter
         → scatter event.query() 成功
         → 层组 Local 就绪 + 原生 watermark 允许区间复用
```

- 删除了独立接收 worker、`rx-plan / rx-slot / rx-group / rx-ack` journal 和逐组 ACK。Remote 的原有 offer/ready/done 控制和诊断 journal 继续保留。
- 在现有 `STAGING_REQ` 后追加可选层 ID 和 token 起始位置，用显式 group index 标识分配；不按配置 chunk size 推算层组索引。因此仍沿用部署的实际 chunk，兼容原生调度器内部缩小尾块。同 TP 的普通中间 chunk 保持原发送路径。
- 层组按 `[本组 K, 本组 V]` 紧凑布局写 ring。P 保留原生索引映射、Batch 上限、Send Lock、probe、session 和现有私有流 D2H，不额外分配原生异构 TP 路径的全 chunk GPU gather buffers。
- D 在已有 `_scatter_stream` 上将整个已分配区间异步 H2D 到相同偏移的 GPU shadow，再调用现有 Triton scatter（原有 torch fallback 也保留）。事件记录在 scatter 之后；H2D 完成和网络 Success 都不能提前切 Local 或释放 watermark。
- 原生后台接收线程在收到 `CHUNK_READY` 后提交 scatter；普通队列和已经提前准入的 Remote 请求都继续推进事件检查。最终接收完成需同时满足原生 Success、全部分配已消费、scatter events 全部完成。
- 可用 ring 空间允许下组网络传输和上组 H2D/scatter 重叠；发生绕回时按原有 watermark 等待，不新增每组 ACK。后台提交与主线程回收使用同一锁，先排空 scatter 再回收分配。
- 每个 D rank 的固定内存开销：GPU 模式为一份 GPU ring；host 模式为一份 pinned host ring **加一份同容量 GPU shadow**。默认各 4096 MiB，可通过原有 pool size 调整，且单层组必须能装入 ring。超大组失败，不回退到绕过流控的直接写入。

建议对照矩阵（固定 P `HANDOFF_PRE_LAYERWISE_HOST_STAGING=1`）：

| 路径 | P/D `SGLANG_DISAGG_STAGING_BUFFER` | D `HANDOFF_PRE_LAYERWISE_RECV_HOST_STAGING` |
| --- | --- | --- |
| 直接写 KV pool | `0` | `0` |
| 原生 GPU ring＋scatter | `1` | `0` |
| pinned host ring＋H2D＋scatter | `1` | `1` |

保持部署 chunk 大小、group 策略、Batch、请求和采样参数相同，分别测试 `layerwise` 与 `remote` 的 TTFT、Remote Window、每步延迟、E2E、输出一致性和内存峰值。report 增加 `native_staging`，保留 `host_staging` 和 `recv_host_staging`；原生 ring 路径的 `layer-*.json` 标记 `completion=scatter`，仅用于诊断，由 D 查询完成事件后写入，不承担握手或流控。

```bash

  --source-device 0 --destination-device 2 --busy-device destination --native-ring
# pinned host ring 实验组

```

report 同时记录实际 `prefill_chunk_tokens`、发送区间 `final_chunk_tokens` 和采用的 `layer_group_size`，不要求另传部署 chunk size。只有本轮确实采用多个层组时才追加 `--require-overlap`；小 chunk 自动合组的 Remote 对照不应要求跨层重叠。`layerwise` 自动回退的请求没有 activation，不能把它误判成传输失败。

report 的时间均来自同机 monotonic 时钟，汇总延迟对每个 room 取最慢 TP rank。`prefill.json` 是采样结束后 finalization 的控制时间；层完成早于它是传输重叠的辅助证据，不等于精确 GPU kernel overlap。`observed_remote_window_ms` 是准入到控制器观察到全部层 ready 的时间，受 polling interval 影响；必须结合 Remote 调用数与 GPU trace。报告不能替代 TTFT/ITL/E2E benchmark。

journal 为实验取证保留，不自动删除。等所有角色停止且 released 数等于 activated 数后归档该轮目录；不要在活跃请求中清空目录。`off` 组没有 activation，report 的 require 检查不适用。

## 对照实验与验收

| 组 | mode | group size | 要回答的问题 |
| --- | --- | --- | --- |
| A | off | 无 | 原生 PD 基线 |
| B | layerwise | auto | Prefill 传输重叠本身的收益；小尾块自动走原生路径 |
| C | remote | 模型总层数 N | 相同新控制路径、无跨层计算重叠的 Remote 对照 |
| D | remote | auto | Layerwise + Remote 的组合收益；小尾块合成一组保留 Remote |

C 的所有层在一次 split 调用中完成再提交发送，不能将其直接标为原封不动的 P5.18 基线。现有 P5.18 的 D0→D1 迁移可另测；它与本实验的 P→D 路径、router 不同，不宜混入同一主表。

如果现有部署使单请求的实际尾块一直小于 3072，B 会回退到 A，D 会与 C 使用同样的单组策略。这是预期行为，不为制造重叠而修改部署 chunk size；可通过正常的多请求 batch 检查总量是否跨过门槛。

固定同一组 prompt、seed、输出长度和请求到达序列，预热后每组至少重复 3 轮并交替执行：

- 输入长度：2K / 8K / 32K；输出长度：128 / 512；并发：1 / 4 / 8。
- 固定部署 chunk 配置；若部署启用 token 分块，围绕其有效大小测试输入长度 `chunk−1`、`chunk`、`chunk+1`、`2×chunk+17`，同时记录实际每轮 token 数。
- group size 默认 auto；归因对照可覆盖为 4 / 9 / 12 / N（36 层模型），只调整层分组，控制发送次数和文件通知开销。
- 先 TP1，再 TP2；含混合长度 batch、连续多轮复用槽位、客户端早退、传输失败。

正确性门槛：输出与 A 一致（若浮点路径改变导致 greedy 分歧，比较逐 token logprob 并定位首个分歧，不能仅忽略）；无重复响应；无缺层本地读；故障不发布完成证明；正常请求 drain 后所有源 lease / metadata slot 归还。传输故障首版预期 fail closed，不能声称服务自动恢复。

主指标记录 p50/p95/p99 TTFT、ITL、E2E、吞吐和错误数；归因记录 P finalize→D first step、剩余 KV 时间、Remote Window、Remote 调用数、CPU 控制开销和 GPU 计算/传输重叠。只在错误率不升、结果正确、D 相对 B/C 有稳定收益时，判断 Remote 提前准入值得保留。
