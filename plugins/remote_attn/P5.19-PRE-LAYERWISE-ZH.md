# P5.19：Prefill Layerwise KV Transfer + Remote Attention

这版是默认关闭的同机实验接入，基于 `remote-attn` 的 `e1a133fc08`。
参考 [SGLang PR #34905](https://github.com/sgl-project/sglang/pull/34905)
的 `a57f4613803fd099a3a90a2defafcb01d17bd57c`：复用 split-prefill，层组计算结束后记录 CUDA event，传输线程等待 event 后发送该组 K/V。
没有整体 cherry-pick 上游 PR，也没有移植其中 hybrid / speculative 支持。
CPU 合约测试不代表 GPU 正确性或性能验收；当前尚无这版的 CUDA E2E 性能结论。

## 接入位置与所有权

- `sglang_remote_attn/pre_layerwise.py`：Scheduler 实例持有控制器；负责最终 chunk 的层组计划、提前准入、TP 一致回收和 journal。
- `handoff_control.py`：复用 RemoteHub、epoch、RPC 引用租约和已有的 attention wrapper；新增可选 release 回调，让原生 PD 保留 KV 分配的最终所有权。
- `hooks.py`：薄封装 `run_batch`、`ModelRunner.forward`、`send_kv_chunk`、`pop_transferred` 和 idle 判断；不复制调度循环。
- Mooncake：可选 `kv_buffer_indices` 只选相同布局的指针；`on_complete` 在全部目的端写成功后执行。失败、取消、目的范围不足均不能发布层完成证明。
- Decode：`_commit_transfer_to_req(..., keep_receiver=True)` 提前使用首 token 元数据，但保留 receiver 和 metadata slot 到真实传输完成。

P 在最终 chunk 开始计算前为整段尾部索引预留一次发送区间。每个层组结束即提交指定 K/V buffer 的任务。P 完成采样后，独立发送首 token 元数据并发布 Remote 服务地址；随后仍向同一原生 FIFO 提交最终 metadata 任务。**没有提前伪造 `KVPoll.Success`。**

D 收到匹配 generation 的 ready 标记、确认本地 metadata 的 bootstrap room 正确，并在全部 TP rank 同意后，使用已有的原生 Req 开始 decode。已完成层走本地 attention，其余层用 P 的前缀加 D 的本地 tail 做 Remote Attention。P 的 HTTP 侧使用一次性的 response snapshot 提前结束，活的 Req 继续等待真实传输完成，避免 router 等到全部 KV 传完才转发 D 的结果。

P 的 KV 释放需同时满足：原生发送结束、D 已退出 Remote、在途 RPC 读引用归零；实际释放在 TP 全体确认后进行。D 在原生传输成功前不清 receiver、不归还 metadata slot。取消时先 drain；超时或无法证明写入结束则报错并保留分配，首版没有在线恢复协议。pending lease 会阻止 idle cache reset。

## chunk size 的含义

支持原生 `--chunked-prefill-size`，与 `HANDOFF_PRE_LAYERWISE_GROUP_SIZE` 独立：前者按 token 分块，后者按层分组。

- 中间 token chunk 沿用原生整层发送。
- **只有最终 token chunk 按层组流水发送**，包括不足 chunk size 的尾块。
- 同 room 的原生任务使用同一 FIFO；最终 chunk 的某层组写入完成时，前面的普通 chunk 已结束。因此该层的证明覆盖完整前缀 `[0, prompt_len)`。
- 不把“某层发送已提交”当作“完整前缀已经可读”，不重复发送整个最终 chunk。
- batch 中含中间 chunk 时仍可执行 split-prefill，但只为合格的最终 chunk 提交层组发送；有 embedding override / hidden-state capture 的 batch 沿用普通路径。

小 chunk 下，前面大部分 KV 已由普通发送隐藏，最终 chunk 较短，这个优化可能收益很小；不要只用一个 chunk size 判断有效性。

## 开关与运行

两端安装本工作树的 SGLang 和插件。原有插件仍需 `SGLANG_PLUGINS=remote_attn`、各角色独立的 `HANDOFF_CTL_DIR`。
新增配置必须在 P/D 一致设置：

| 变量 | 默认值 | 含义 |
| --- | --- | --- |
| `HANDOFF_PRE_LAYERWISE` | `off` | `off` 保留原路径；`layerwise` 边算边传但等待完整 KV；`remote` 启用提前准入与 Remote |
| `HANDOFF_PD_DIR` | 无 | P/D 可见的同一个本机绝对目录，按 room/rank/generation 隔离 |
| `HANDOFF_PRE_LAYERWISE_GROUP_SIZE` | `4` | 每组层数；尾组可不足该值 |
| `HANDOFF_PD_DRAIN_TIMEOUT_S` | `300` | 活跃源租约与清理等待上限；不能小于实际长请求耗时 |

首版范围：Qwen3ForCausalLM、dense NHD MHA BF16/FP16、CUDA、相同 TP 宽度、PP=DP=CP=1、page size 1、关闭 radix cache / overlap scheduler / CUDA graphs（含 TP1），Mooncake 同布局单目的端、early allocation。LoRA、embedding override 的流水路径、KV checksum、staging、host receive、HiCache、统一 KV、PD multiplexing、speculative 不支持。开关不匹配或 offer 尚未就绪的请求走原生路径，必须检查实际 activation 数量。

这是同机共享目录控制协议；KV 仍走原生 Mooncake。不能直接用于跨机部署。逐层完成在调度步之间刷新，本路径禁用按 RPC 耗时切换为阻塞 layer-wait；后续可增加异步通知优化。不要同时向这些 Req 发 P5.18 freeze/migrate 控制命令。

下面复用现有的 TP2 P / D0 启动脚本（总计四张 GPU），不启动 P5.18 D0→D1 gateway：

```bash
# P、D 两个终端都设置；每一轮使用独立的新目录。
export HANDOFF_PRE_LAYERWISE=remote
export HANDOFF_PD_DIR=/workspace/p519/run01/journal
export HANDOFF_CTL_ROOT=/workspace/p519/run01/control
export HANDOFF_PRE_LAYERWISE_GROUP_SIZE=4
export HANDOFF_MODEL_PATH=/workspace/models/Qwen3-8B
export HANDOFF_PYTHON=/opt/conda/envs/sglang/bin/python

# P 终端（脚本默认 GPU 0,1）
bash plugins/remote_attn/deploy/start_p511_p_tp2.sh

# D 终端（脚本默认 GPU 2,3）
bash plugins/remote_attn/deploy/start_p511_d0_tp2.sh

# 第三个终端：使用已安装的原生 PD router。
python -m sglang_router.launch_router --pd-disaggregation \
  --prefill http://127.0.0.1:31016 35409 \
  --decode http://127.0.0.1:31017 --host 127.0.0.1 --port 31000
```

修改 chunk size 可在两端启动脚本后追加 `--chunked-prefill-size 8192`。所有对照组保持相同 graphs、TP、transport、profiling 和内存配置。先用 temperature=0 的相同 input_ids 请求比较完整输出，再做吞吐测量。现有启动脚本默认打开 RPC profiling，正式性能轮建议两端统一 `HANDOFF_RPC_PROFILE=0`，另跑一轮开 profiler 的归因实验。

```bash
python -m sglang.bench_serving --backend sglang \
  --host 127.0.0.1 --port 31000 --tokenizer /workspace/models/Qwen3-8B \
  --dataset-name random --random-input-len 8192 --random-output-len 128 \
  --random-range-ratio 1 --num-prompts 100 --max-concurrency 1 \
  --request-rate inf --output-file /workspace/p519/run01/bench.jsonl

# 等请求与清理结束后运行。require 参数用于确认确实覆盖了目标路径。
python test/manual/remote_attn/pre_layerwise_report.py \
  /workspace/p519/run01/journal --require-remote --require-overlap \
  > /workspace/p519/run01/handoff.json
```

report 的时间均来自同机 monotonic 时钟，汇总延迟对每个 room 取最慢 TP rank。`prefill.json` 是采样结束后 finalization 的控制时间；层完成早于它是传输重叠的辅助证据，不等于精确 GPU kernel overlap。`observed_remote_window_ms` 是准入到控制器观察到全部层 ready 的时间，受 polling interval 影响；必须结合 Remote 调用数与 GPU trace。报告不能替代 TTFT/ITL/E2E benchmark。

journal 为实验取证保留，不自动删除。等所有角色停止且 released 数等于 activated 数后归档该轮目录；不要在活跃请求中清空目录。`off` 组没有 activation，report 的 require 检查不适用。

## 对照实验与验收

| 组 | mode | group size | 要回答的问题 |
| --- | --- | --- | --- |
| A | off | 无 | 原生 PD 基线 |
| B | layerwise | 4 | Prefill 传输重叠本身的收益 |
| C | remote | 模型总层数 N | 相同新控制路径、无跨层计算重叠的 Remote 对照 |
| D | remote | 4 | Layerwise + Remote 的组合收益 |

C 的所有层在一次 split 调用中完成再提交发送，不能将其直接标为原封不动的 P5.18 基线。现有 P5.18 的 D0→D1 迁移可另测；它与本实验的 P→D 路径、router 不同，不宜混入同一主表。

固定同一组 prompt、seed、输出长度和请求到达序列，预热后每组至少重复 3 轮并交替执行：

- 输入长度：2K / 8K / 32K；输出长度：128 / 512；并发：1 / 4 / 8。
- chunk size：2048 / 8192 / 覆盖完整输入的大小；额外测试 `chunk−1`、`chunk`、`chunk+1`、`2×chunk+17` 的边界。
- group size 先固定 4，验证后扫 1 / 2 / 4 / 8 / N；控制发送次数和文件通知开销。
- 先 TP1，再 TP2；含混合长度 batch、连续多轮复用槽位、客户端早退、传输失败。

正确性门槛：输出与 A 一致（若浮点路径改变导致 greedy 分歧，比较逐 token logprob 并定位首个分歧，不能仅忽略）；无重复响应；无缺层本地读；故障不发布完成证明；正常请求 drain 后所有源 lease / metadata slot 归还。传输故障首版预期 fail closed，不能声称服务自动恢复。

主指标记录 p50/p95/p99 TTFT、ITL、E2E、吞吐和错误数；归因记录 P finalize→D first step、剩余 KV 时间、Remote Window、Remote 调用数、CPU 控制开销和 GPU 计算/传输重叠。只在错误率不升、结果正确、D 相对 B/C 有稳定收益时，判断 Remote 提前准入值得保留。
