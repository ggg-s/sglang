# 分段 Prefill V2 的 RTX 5090 实测

数据来自 2026-11-12 至 11-13 的 39 机实验，使用 RTX 5090 GPU 4–7、
Qwen3.8-27B-FP8、P TP2 / D TP2、Mooncake TCP、CUDA Graph 和 overlap。
闭环并发为 C4，每请求固定输出 128 token。V2 实验从 `222bf7b2c5` 派生，
入库前的 V1 对照默认 cut 0.75 见 `9733758372`。
以下延迟均为 ms，吞吐为输出 token/s。

## 策略

P 在匹配缓存后选择 `min((N + H + 12185) // 2, N - floor)`。
`H` 是实际命中前缀，`floor = min(2048, max(N // 16, 1))`。
若 cut 没越过命中前缀或低于 D 声明的下界，请求走原生 PD。
V2 可将超过 4096 token 的后缀分块处理。4096 是默认单块上限。

D 优先调度已有 decode。候选后缀有名额且当前有活跃 decode 时，
每次让路计一次 `next_batch()`。通常预算为 150 次，P 实际命中至少 70%
时最多 45 次。预算按块重置，满批等待发生在预算之外。
各 TP rank 使用相同的请求与计数，`time.monotonic()` 只用于日志。
命中率读取 P 传来的 `cached_tokens`，D 的 `prefix_len` 在接收后指向 cut。

平衡公式把 D 的 decode 工作折算成 12,185 个 prefill token，
来自 128 步 × 14 ms/步 × 6,800 token/s。换输出长度、模型、TP 或硬件后
需要重新验证这项标定。只有 D 宣告 decode 优先能力时 P 才用平衡公式。

## 调度开关对照

打断率指逐请求最大 ITL 超过 100 ms 的比例。打断率为零时，
受影响子集的 p90 留空。32K 的 150/600 次和 64K 的优先调度臂分别记录到
全体请求最大 ITL 的 p90 约 42 ms 和 41 ms。

## 切点扫描

预算 150 次。64K 扫描的实际输入为 65,408 token，32K 为 32,768 token。
平衡点在两组中都有最低的实测 TTFT p90。64K 的 0.65 臂 E2E 低 0.6%，
吞吐高 0.9%，TTFT p90 高约 9.0%。

## 对照配置

- 两侧使用默认值可复现 V2 的策略。D 侧用 `HANDOFF_SPLIT_DEFER_TICKS=0`
  可恢复 V1 的立即提交和默认未命中比例。
- 固定 cut 比较调度时，在 P 设 `HANDOFF_SPLIT_SUFFIX_TOKENS`，
  例如 64K 同切点对照用 26612，在 D 分别设预算 0 和 150。
- 每臂用唯一标签保存请求记录，同时计算打断率和受影响子集的最大 ITL p90。
