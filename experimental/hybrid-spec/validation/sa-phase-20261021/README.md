# 4060 SA 更新/查询分阶段计时与异常调查

日期：2026-10-21。GPU：RTX 4060 Laptop 8 GiB；PyTorch 2.14.1+cu130、CUDA 13.0。
同一份 v6 精确频次算法，完整 32 位布局约108字节/token，压缩布局约72字节/token。
本轮没有修改生产源码或部署服务；只增加可复现的私有 JIT 微测入口。

## 结论

16K 场景中，压缩布局的独立更新耗时减少 **12.7%～15.1%**；实际展开候选的
查询耗时减少 **1.2%～9.2%**，查询绝对收益仅约0.03～0.63 μs。主要收益来自更新。
1K 的更新减少约11.0%～14.2%，实际查询减少约2.4%～8.0%。

此前 16K/单一token/4请求的2.945倍异常，本轮 kernel 级合计结果为
**16.474 → 15.604 μs，减少5.3%**，未出现稳定的三倍 kernel 退化。
确认旧外围事件法存在明显提交/调度间隙污染；原那一次没有同步 trace 与遥测，
仍不能唯一归因。以下 kernel 级计时比之前外围 CUDA-event 数值更适合比较计算耗时。

## 怎么拆分、怎么计时

- 更新：使用生产 `finalize_shared_kernel`，`final_lengths=-1`，只消费暂存的9个
  accept token 并更新同一套自动机/精确频次；保留代际与版本检查。
- 查询：在完全相同的更新后状态上运行生产 `consume_query_kernel`，pending=0，
  跳过追加；保留输出初始化、资格检查和最多8个候选的生成。
- 融合对照：运行原来的 `consume_query_kernel`，一次完成追加与查询。
- 独立阶段增加一次 kernel 边界并重复部分检查，更新与查询时间**不可相加**来
  预测融合执行时间。两种布局只在同一阶段内比较。
- 所有比较使用确定性相同输入、相同词表/代际/反馈、相同预分配缓冲。恢复 GPU
  状态在计时区间外；同一case的两种布局同时保留，消除分配顺序逐轮变化。
- CUDA-event 实验每形状5轮、每轮每布局每阶段60次，逐样本交换布局顺序；同时
  记录 Graph内/外事件、Python replay调用时长、墙钟时间与nvidia-smi遥测。
- 最终表格使用 **CUPTI kernel自身起止时间**，排除CPU提交间隙、状态恢复和
  CUDA-event节点之间的间隙。每形状5轮，每轮每布局每阶段20个kernel；逐轮反转
  布局先后顺序，报告五个单轮中位数的中位数。13个形状共10400个SA kernel，
  trace中每阶段/布局唯一Graph ID均核对样本总数，没有丢弃慢样本。

## 原匹配门槛4的路径

2种token与单一token的门槛4查询结果见 `summary.json` 的 `query` 字段。
64种token的本组历史最长只匹配2个token，因此会在生成候选前回退；这些场景
不是完整的续写查询。在16K/request=1时两布局均2.090 μs，request=4均1.997 μs。
不能把这些回退路径的约2 μs描述为“查出8个候选”的耗时。

## 异常调查

### 原异常场景的 kernel 级复测

16K、单一token、4请求：

| 阶段 | 32位 μs | 72字节 μs | 耗时减少 |
|---|---:|---:|---:|
| 更新 | 15.599 | 13.504 | 13.4% |
| 查询，门槛4 | 2.563 | 2.532 | 1.2% |
| 原融合kernel | 16.474 | 15.604 | 5.3% |

查询差异只有约0.031 μs，应保守理解；不能据此宣称明显的查询加速。
13个形状的阶段状态、全部逻辑字段、转移、候选和eligibility在两布局间一致，
独立更新后的状态也与融合路径一致。两轮完整实验均exit=0。

### 同一次回放的内外计时

事件实验中，同一宽布局融合回放出现过 **Graph外450.688 μs、Graph内21.504 μs**；
另一个样本为外201.984 μs、内21.504 μs。压缩布局也出现外83.104 μs、内20.480 μs。
它们证明外围事件区间包含了足以放大微秒任务的提交/调度等待，并非等于kernel时间。

把事件放入Graph仍有event节点和调度间隙：空Graph内两次event记录的中位间隔
3.072 μs，最大50.176 μs，所以最终没有把Graph内event时间作为短查询的权威数值。
额外注入1 ms主机等待后，宽布局外计时约1298 μs、内约31.6 μs；压缩布局外约
1254 μs、内约28.7 μs，进一步验证外围口径对主机等待敏感。该注入是诊断对照，
没有混入性能汇总或kernel结果。

### 时钟、功耗与长布局对照

事件实验SM时钟2250～2490 MHz、47～53°C、23.44～35.06 W；最终profiler实验
2250～2505 MHz、40～45°C、23.69～27.71 W。采样点均为P0，显存时钟8000 MHz。
没有修改锁频/功耗设置；遥测约100 ms级，不能排除未被采到的短时波动，
也不能用本轮温度为此前没有遥测的异常定因。

容量32768时，两组都自动使用32位布局，作为负对照：更新均194.125 μs；
查询7.622/7.590 μs；融合199.657/199.721 μs。该对照未出现大幅布局差异。

## 复现与证据

基准：[benchmark_sa_phases_cuda.py](../../benchmarks/benchmark_sa_phases_cuda.py)。
`--profile`使用CUPTI读取实际kernel时间；不加该参数则采集Graph内/外event对照。
示例：

```bash
PYTHONPATH=experimental/hybrid-spec/src python \
  experimental/hybrid-spec/benchmarks/benchmark_sa_phases_cuda.py \
  --output /tmp/sa-phases --profile --rounds 5 --samples 20
```

`summary.json`包含全部阶段及五轮中位数；`manifest.json`包含原生产源码和基准
摘要、时钟功耗范围、异常样本和注入对照；`evidence.tar.gz`保存13份压缩Chrome
trace、原始事件/CUPTI样本、遥测、运行脚本与私有JIT源码。

首次profiler汇总曾混入同名GPU annotation，随后严格用CPU时间窗口又因CPU/GPU
时间转换的微小偏差漏掉窗口末尾一个kernel。最终按唯一Graph ID归属、按每图
完整100个kernel核对；两次汇总失败日志保留，最终trace没有按耗时过滤或删样本。

本结果仅是GPU SA组件。没有测CPU prompt构建/H2D、feedback生产kernel、
TP通信、neural/target模型、TPOT或服务吞吐，不能据此推算端到端加速。
