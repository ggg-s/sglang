分支 `codex/dsv4-pdmux-latest-main`，单卡 RTX 6000D（156 SM / 96 GB）。

所有数字均为实测。标注「失效配置」的段落是在前缀缓存被意外关闭的状态下测的，仅作对照保留。

| | 无 PDMux | 有 PDMux | Δ |
|---|---:|---:|---:|

## 11. P=200（工作集超出 GPU 容量）

GPU 只能缓存 80 条前缀（336 − 64×4），200 条必然抖动。

| 组 | QPS | RPM | tok/s | TTFT p50 | TTFT p95 | TPOT | 命中 |
|---|---:|---:|---:|---:|---:|---:|---:|
| base | 2.53 | 152 | 324 | 11,288 ms | 20,394 ms | 108.6 ms | 20.2% |
| base+hicache（16 GB） | 2.46 | 148 | 315 | 11,920 ms | 21,485 ms | 109.2 ms | 20.9% |
| base+mtp+hicache+pdmux | 2.23 | 134 | 286 | 23,843 ms | 25,369 ms | **35.8 ms** | 20.2% |
| **base+hicache（64 GB）** | **6.66** | **400** | **853** | **795 ms** | 18,495 ms | 48.1 ms | **83.3%** |

HiCache 16 GB 只买到 578,796 token 的主机 KV；需要约 3.18M（200×12k 前缀 + 64×12k 运行态），故无效。64 GB 下主机 KV 达 2,315,184 token（47.41 GB），命中率饱和（4/5 重复全命中 ≈ 80%，加共享 system prompt ≈ 83%）。

### HiCache 起效判据

```
主机 KV 容量 ≥ P × L − (GPU KV 总量 − 并发 × L)
```

P=200、L=12k 时约需 33 GB，实测给 47 GB 即打满。

## 12. 长上下文验证（32K）

目的：验证 PDMux 的相对收益是否随上下文长度增长。

负载用 `build_long.py` 从同一数据集切出 ~31.5K 的 tool-cut 前缀。首轮取 P=40（工作集 1.256M），但 MTP 组的 KV 池只有 1.196M（draft KV 占内存），小于工作集导致抖动，命中率 base 96.2% / pdmux 84.6%，对比不干净，作废。改为 P=30 重跑。

**有效数据**（P=30，工作集 945,114 token，并发 32，1020 请求）：

| 组 | QPS | RPM | tok/s | TTFT p50 | TTFT p95 | TPOT | 命中 |
|---|---:|---:|---:|---:|---:|---:|---:|
| base | 5.66 | 340 | 724 | 308 ms | 359 ms | 36.3 ms | 97.1% |
| mtp+pdmux | 7.51 | 451 | 961 | 392 ms | 6,151 ms | 19.8 ms | 97.1% |

两组命中率相同（97.1%），对比干净。

**作废的 P=40 数据（保留记录）**：base 5.19 QPS / 311 RPM / 命中 96.2%；mtp+pdmux 3.02 QPS / 181 RPM / 命中 84.6%。KV 池：base 1,548,200；MTP 组 1,195,810 < 工作集 1,256,003。

### 上下文长度对 PDMux 相对收益的影响

| 上下文 | base RPM | pdmux RPM | 吞吐增益 | TPOT 改善 | TTFT p95 变化 |
|---|---:|---:|---:|---:|---:|
| 12K | 708 | 852 | +20.3% | −33.7%（33.8→22.4 ms） | +104%（5,495→11,215 ms） |
| 32K | 340 | 451 | **+32.6%** | **−45.5%（36.3→19.8 ms）** | **+1,613%（359→6,151 ms）** |

上下文越长，每个 token 位的成本越高（attention 要扫更长的 KV），PDMux 通过 kernel 级并发压缩每位置成本的绝对空间也越大——PDMux 的相对收益随之变大，但 TTFT 尾部代价同步放大。注意这条只在命中率高、并发未打满时成立；32K + 64 并发时该收益转为 −8.6%（第 13b 节 C2）。

### 无 MTP 的长上下文对照（排除 draft KV 损耗）

不开投机就没有 35 万 token 的 draft KV 占用，base 的 KV 池保持 1,548,200，故 64K 也能装下（P=20、并发 20、工作集约 1.28M）。

| 上下文 | 组 | QPS | RPM | tok/s | TPOT | TTFT p50 | TTFT p95 | 命中 |
|---|---|---:|---:|---:|---:|---:|---:|---:|
| 12K | base | 11.81 | 708 | 1,511 | 33.8 ms | 334 ms | 5,495 ms | 95.6% |
| 12K | base+pdmux | 10.21 | 613 | 1,307 | 40.0 ms | 236 ms | 7,693 ms | 95.6% |
| 32K | base | 5.66 | 340 | 724 | 36.3 ms | 308 ms | 359 ms | 97.1% |
| 32K | base+pdmux | 5.37 | 322 | 687 | 36.2 ms | 224 ms | 2,342 ms | 97.1% |
| 64K | base | 3.35 | 201 | 429 | 37.4 ms | 312 ms | 392 ms | 98.0% |
| 64K | base+pdmux | 3.23 | 194 | 414 | 35.9 ms | 221 ms | 332 ms | 98.0% |

PDMux 单独开的吞吐差：12K −13.4% → 32K −5.3% → 64K −3.5%，**收敛到 0 但不会变正**。

三条结论：

1. **长上下文放大 PDMux 收益只在配 MTP 时成立**。32K 的 +33% 来自 MTP，`base+pdmux` 在 32K 仍是 −5%。"decode 变访存受限、空出算力给 prefill"的推演在本模型上不成立。
2. **PDMux 单独在 64K 反而改善了 TTFT**（p50 312→221 ms，p95 392→332 ms）。这是全实验唯一一次不伤 TTFT 的配置：并发 20、命中 98%，系统余量充足，prefill lane 不饿。**PDMux 的 TTFT 代价源于满载，而非 PDMux 本身。**
3. **decode 成本对上下文长度几乎不敏感**：每并发请求吞吐 12K 23.6 → 32K 22.6 → 64K 21.5 tok/s，上下文放大 5 倍只降 9%。MoE（A3B 激活 3B）下 attention 占比小，这是 PDMux 单独吃不到长上下文红利的原因。

### 附：MTP 组 KV 池小于 base 组

同一配置下 `max_total_num_tokens`：base 1,548,200，MTP 组 1,195,810（32K 上下文）。draft 模型的 KV 占用约 35 万 token 容量，做长上下文容量规划时必须计入。

## 13. 真实 agent 负载：需不需要 HiCache

负载用 `build_realmt.py` 构造：**64 个 agent，每个推进自己的轨迹、最多 12 轮，共 502 条请求**，平均 prompt 8,635 token，峰值工作集 820,837 token。请求按**轮次优先**排序（先发全部 64 条的第 0 轮，再发第 1 轮……），并发槽位 64 = agent 数，复现真实 agent 车队形态。轨迹分组排序会让同一轨迹多轮并发、人为抬高命中率，不采用。

三组配置完全相同（MTP + PDMux + 336 槽 + 64 并发 + `extra_buffer_lazy`），只改主机缓存：

| 组 | QPS | RPM | tok/s | TTFT p50 | TTFT p90 | TPOT | 命中 |
|---|---:|---:|---:|---:|---:|---:|---:|
| **no_hicache** | **11.11** | **667** | 1,422 | 896 ms | 4,120 ms | **34.9 ms** | **83.5%** |
| hc16 | 10.76 | 646 | 1,378 | 899 ms | 4,410 ms | 36.2 ms | 83.6% |
| hc64 | 10.50 | 630 | 1,344 | 970 ms | 4,412 ms | 37.0 ms | 83.6% |

命中率 83.5% → 83.6% → 83.6%：**给到 64 GB 主机内存只提升 0.1 个百分点，QPS 反而降 5.5%。**

### 为什么 HiCache 无效

83.5% 是这份负载的**天然上界**，不是容量不足导致的：

```
总 prompt token     = 502 × 8,635 = 4.33M
每轮真实新增内容    ≈ (14,000 − 4,000) / 11 ≈ 909 token
turn 0 冷启动       ≈ 4,000 token

必然未命中 = 64 × 4,000 + 438 × 909 ≈ 654k → 15.1%
命中率上界 ≈ 84.9%（实测 83.5%，吻合）
```

那 16.5% 全是每轮真实新增的工具返回与 assistant 回复，从未被计算过。HiCache 只能救"装不下被挤掉"，救不了"本来就没有"。

而且容量本就富余：

```
工作集 820,837 token  <  KV 池 989,986
Mamba 空余 80 槽      ≥  活跃前缀 64 条
```

没有驱逐，HiCache 无事可做，只剩主机↔设备的搬运开销。

### chunked-prefill-size 与 PDMux 分段粒度

早期所有实验都显式设 `--chunked-prefill-size 16384`，后被指出应是配置假象，遂用默认值（服务器解析为 **8192**）重跑五组：

| 组 | QPS | RPM | TTFT p50 | TPOT | | QPS(16384) | TTFT p50(16384) |
|---|---:|---:|---:|---:|---|---:|---:|
| base | 9.29 | 557 | 1,957 ms | 38.1 | | 553 | 2,286 ms |
| base+hicache | 8.81 | 528 | 2,241 ms | 38.8 | | 527 | 2,577 ms |
| base+mtp | 9.39 | 563 | 314 ms | 47.8 | | 571 | 281 ms |
| base+mtp+hicache | 9.16 | 550 | 290 ms | 49.1 | | 563 | 311 ms |
| base+mtp+hicache+pdmux | **10.80** | **648** | 1,046 ms | 35.3 | | 645 | 904 ms |

`chunk 16384 → 8192` 后 QPS 全部落在噪声范围内，TTFT 仅 ±15% 波动。**该参数不是性能杠杆。**

顺带验证 PDMux 分段粒度：`forward_count = min(remaining_layers, split_forward_token_budget // prefill_tokens)`，再被 `split_forward_max_layers` 截断（`multiplexing_mixin.py:334-390`）。chunk=16384 配 budget 131072 → K=8；chunk=8192 配 131072 → K=16；固定 chunk=16384、把 budget 提到 262144 同样得到 K=16，且可避免同时改动批处理。

| PDMux 配置 | K | RPM |
|---|---:|---:|
| chunk 16384 | 8 | 645 |
| chunk 8192（默认） | 16 | 648 |

K=8 与 K=16 吞吐相同，**分段粒度也不是杠杆**。

三个假设（长上下文放大 PDMux 单独收益、大批次 prefill 导致 base TTFT 差、chunk/K 是性能杠杆）均被实测推翻；但主结论在三轮参数扰动下保持不变：PDMux 最优（+16~20%）、HiCache 负收益、MTP 单独接近中性。

### 未解释现象：base 的 TTFT 比 +mtp 差 8 倍

`base` 的 TTFT p50 为 2,286 ms，而 `base+mtp` 仅 281 ms，但两者吞吐只差 3.3%、prefill 量相同。

已定位到队列层：

| | base | +mtp |
|---|---:|---:|
| prefill 批次数 | 57 | 224 |
| 每批平均请求数 | 8.8 | 2.2 |
| prefill 时刻的 `#queue-req` | **19.7** | **1.5** |
| 稳定态运行请求数 | 61 | 62 |

base 以大批次（每批约 9 个请求）集中 prefill，请求平均排在 20 个之后；mtp 批次小、频率高，队列只有 1.5。TTFT 差距即来源于此。

TTFT 与队列深度、完成速率满足 `TTFT ≈ queue_depth / QPS`：base 19.7/9.29 ≈ 2.1 s（实测 1.96 s），mtp 1.5/9.39 ≈ 0.16 s（实测 0.31 s）。

但**为什么 base 的队列稳定在 20、mtp 只有 1.5，仍未定位**。已排除的解释：

- **不是 prefill 批次大小**：chunk 从 16384 减到 8192（每批请求数 9.5→5.7），base 的 TTFT 只降 14%，QPS 不变；
- **不是槽位周转**：mtp 每请求占用槽位时间更长（128×47.8 ms = 6.1 s vs 128×38.1 ms = 4.9 s），队列本应更深；
- **不是 KV 容量**：mtp 的 KV 池更小（989,628 vs 1,549,224），若 KV 是约束，mtp 应更差；
- **不是吞吐**：两者 QPS 相差 1%（557 vs 563）。

按 Little's law，base 与 mtp 的在飞请求数都接近 64，但 base 是"少量快请求 + 深队列"（~45 运行 / 20 排队），mtp 是"多量慢请求 + 浅队列"（~61 运行 / 3 排队）。这个分配差异的**调度器层面成因未确认**，需逐迭代埋点（记录每请求从入队到进 prefill 的等待时长）才能归因。在此之前，不应据此对未开投机的部署做选型建议。

### 结论

**在 12K、工作集小于 GPU 容量时不要开 HiCache**：命中率的上限由负载的增量内容决定，此时没有可捞的回用，主机缓存只带来搬运开销。省下的内存应给 `max-mamba-cache-size`——槽数直接决定并发上限。

**该结论不适用于工作集超出 GPU 容量的场景**，见 [第 13b 节](#13b-32k-真实负载hicache-写入策略才是关键)：32K 下 HiCache 配合 `write_back` 能把命中率从 60.2% 拉回 85.1%、吞吐 141→288 RPM。

**真实 SWE 负载下的推荐配置**：MTP + PDMux，不开 HiCache，336 槽，64 并发 → 667 RPM / TPOT 34.9 ms。

附带验证：真实负载 667 RPM，是合成 P=50 负载 852 RPM 的 78%，与按命中率插值的 300–420 RPM 估计一致。

另注：前几轮遇到的"命中率塌到 20%"灾难都来自合成负载（P=200 条独立前缀超出容量）或 Mamba 槽配置过少，真实 agent 场景下 64 个并行会话的工作集反而更小。

## 13b. 32K 真实负载：HiCache 写入策略才是关键

负载：64 agent × 12 轮，轮次阶梯 8,000→30,000 token，平均输入 18,593，634 请求，并发 32，336 Mamba 槽。

### 三组基础对比

| 组 | QPS | RPM | tok/s | TTFT p50 | TTFT p90 | TPOT | 命中率 |
|---|---:|---:|---:|---:|---:|---:|---:|
| base（无投机） | 4.39 | **263** | 562 | 2,438 ms | 3,844 ms | 36.6 ms | **85.0%** |
| mtp+pdmux | 2.35 | 141 | 300 | 2,378 ms | 31,329 ms | 33.4 ms | 60.2% |
| mtp+pdmux+hc32 | 2.18 | 131 | 279 | 2,218 ms | 34,696 ms | 35.4 ms | 58.8% |

### 逐轮命中率揭示了崩溃点

| 轮次 | 平均输入 | agent 数 | 所需缓存 | base (1.548M) | MTP (1.196M) |
|---|---:|---:|---:|---:|---:|
| t5 | 20,725 | 64 | 1.33M | 87.6% | 84% |
| **t6** | 23,211 | 63 | **1.46M** | 88.3% | **54%** |
| **t7** | 24,838 | 59 | **1.47M** | 91.8% | **18%** |
| **t8** | 26,538 | 54 | **1.43M** | 92.0% | **10%** |
| t9 | 27,509 | 38 | 1.05M | 92.3% | 80% |
| t10 | 28,611 | 26 | 0.74M | 92.5% | 93% |

崩溃精确落在需求量 1.43–1.47M 的区间：MTP 池 1,195,810 低于该需求，base 池 1,548,200 略高于它。t9 之后 agent 数下降、需求回落，两组命中率同时恢复。

### 无 MTP 时 base 已贴近理论上限

理论上限 = 上一轮长度 ÷ 本轮长度。t0–t6 实测与上限差距 ≤1 个点，t7–t11 差 2–4 个点，总体 85.0% 对上限约 86.5%。此时 `base+hicache32`（主机 KV 1,157,394 token）命中率仍为 85.0%，QPS 4.24 —— 容量因此不是约束，HiCache 无可救之处。

### 写入策略是决定性变量

同负载、同 MTP+PDMux+32 GB 主机，只改 `--hicache-write-policy`：

| 写入策略 | QPS | RPM | 命中率 | TTFT p50 | t6 | t7 | t8 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 无 HiCache | 2.35 | 141 | 60.2% | 2,378 ms | 54% | 18% | 10% |
| `write_through`（默认） | 2.18 | 131 | 58.8% | 2,218 ms | 48% | 14% | 9% |
| `write_through_selective` | 2.80 | 168 | 69.4% | 2,119 ms | 57% | 50% | 44% |
| **`write_back`** | **4.79** | **288** | **85.1%** | **1,523 ms** | **89%** | **92%** | **92%** |

`write_back` 将崩溃的 t6–t8 从 54%/18%/10% 恢复到 89%/92%/92%，吞吐 131 → 288 RPM（+120%），且 **288 RPM 高于无投机的 base（263 RPM，同命中率 85%）**。

### 32K 完整 2×2 与 TPOT 分析

补齐最后两格后的四组（命中率全部 85% 左右，缓存问题已由 `write_back` 解决）：

| 组 | QPS | RPM | TTFT p50 | TPOT | 命中 |
|---|---:|---:|---:|---:|---:|
| base | 4.39 | 263 | 2,438 ms | 36.6 ms | 85.0% |
| base+pdmux | 4.37 | 262 | **517 ms** | 51.8 ms | 85.1% |
| mtp+hicache(write_back) | 4.59 | 275 | 498 ms | 49.2 ms | 85.0% |
| **mtp+pdmux+hicache(write_back)** | **4.79** | **288** | 1,523 ms | 39.1 ms | 85.1% |

拆解：MTP+HiCache 单独 +4.6%（275 RPM），PDMux 单独 −0.4%（262 RPM），两者合用 +9.5%（288 RPM）。与 12K 不同，32K 下两者接近可加，而非互补。

**TPOT 为何优化不明显**

投机接受率两个负载完全相同，不是原因：

| 组 | accept len | accept rate |
|---|---:|---:|
| 12K +mtp | 3.26 | 0.75 |
| 12K +mtp+pdmux | 3.27 | 0.76 |
| 32K mtp+pdmux | 3.32 | 0.77 |
| 32K +hc(write_back) | 3.32 | 0.77 |

PDMux 对 TPOT 的相对改善并未衰减（12K：47.0→34.9，−26%；32K：49.2→39.1，−21%）。变化的是 base：两个负载下 base 的 TPOT 都是 36.6 ms。12K 时 PDMux 能压到 34.9 险胜，32K 时压到 39.1 无法低于 base。

两项叠加造成：

1. **每请求 prefill 翻倍**：12K 未命中 16.5% × 8,635 = 1,425 token；32K 未命中 15.0% × 18,593 = 2,789 token。PDMux 依靠 kernel 级并发来摊掉这部分工作，量翻倍后可并发的部分摊不完，剩余部分落到 TPOT 上。
2. **并发减半**：12K 用 64、32K 只能 32（KV 限制）。decode 批小一半，每步权重读取成本不变，投机的固定开销摊在 32 个而非 64 个请求上。

结论：**32K 下在无法提高并发时，开 MTP 的 TPOT 是净亏的**（39.1 vs base 36.6）。MTP 的收益依赖大 batch 摊薄固定开销，而长上下文恰恰逼迫降低并发。C 组的真实收益在吞吐（288 vs 263 RPM，+9.5%），不在 TPOT。

### 一种可能的解释：base 的 TTFT 异常被 PDMux 消除

同一现象在两个负载上重现：

| 负载 | base TTFT p50 | base+pdmux TTFT p50 | 改善 |
|---|---:|---:|---:|
| 12K | 2,286 ms | 236 ms | 9.7× |
| 32K | 2,438 ms | 517 ms | 4.7× |

PDMux 消除了 base 那个来源不明的 TTFT 惩罚。这与第 13 节「base 比 +mtp 的 TTFT 差 8 倍」互为印证：base 的高 TTFT 是调度层面的行为（prefill/decode 串行时的队列堆积），PDMux 的分流绕开了它。代价是无 PDMux 时 TPOT 变差（36.6→51.8 ms）。

### 根因

`hiradix_cache.py:856-862`：

```python
# Backup invariant (for write-through mode): backed-up nodes must form a
# contiguous prefix from root — no gaps.  Skip if parent isn't backed up yet;
if not write_back and (node.parent != self.root_node and not node.parent.backuped):
    return 0
```

默认 `write_through` 要求父节点先完成备份才备份子节点。长上下文高压力下，父节点被驱逐的速度快于子节点备份，备份链从中间断开，主机中只剩零散碎片，无法构成完整前缀，因而产生不了命中。`write_back` 在节点被驱逐时才写主机，不受该约束，链路完整。

`write_through_selective` 仅恢复约三分之一（69.4%），说明部分备份不足以构成可命中的完整前缀。

### 对前述结论的修正

第 13 节与第 7 条结论中「生产上不要开 HiCache」不正确，应修正为：

**HiCache 默认的 `write_through` 策略在长上下文高压力下失效；必须改用 `write_back`，HiCache 才能发挥作用。** 12K 场景下 HiCache 无效，是因为工作集本就在 GPU 容量内（命中率已贴近理论上限），与写入策略无关。

## 13c. Trace 证据：并发到底从哪来

三份 torch profiler trace，同一 12K 负载、32 并发，只改配置。分析口径：把 GPU kernel 事件按 CUDA stream 分组，合并区间后计算「多 stream 同时忙」的时长。

| 组 | RPM | CUDA stream 数 | GPU 忙（并集） | **并发内核时间** | 主 stream 平均 kernel |
|---|---:|---:|---:|---:|---:|
| base | 708 | 3 | 94.4% | **3.4%** | 0.043 ms |
| MTP 单独 | 535（−24%） | 5 | 89.5% | **0.5%** | 0.090 ms |
| MTP + PDMux | 852（+20%） | 5 | 94.3% | **24.7%** | 0.181 ms |

### 结论

**并发完全由 PDMux 产生，MTP 不产生并发。**

- MTP 单独时并发仅 0.5%，**低于 base 的 3.4%**。EAGLE 的 draft(×3) → verify 是严格串行依赖，verify 必须等全部 draft 完成，中间插不进任何工作，因此 MTP 单独反而把 GPU 并行度压得更低。
- PDMux 把前向切成 K 层片段分到两条 stream，并发从 0.5% 升到 24.7%（约 50 倍）。

两个组件各提供一个必要条件：

| 组件 | 提供 | 证据 |
|---|---|---|
| PDMux | 重叠的**通道** | 并发 0.5% → 24.7% |
| MTP | 值得重叠的**工作量** | 主 stream kernel 平均时长 0.043 → 0.090 → 0.181 ms |

三个组合的对应结果：

```
只有通道，工作量不足  → base+PDMux = 613 RPM（−13%）
只有工作量，没有通道  → MTP 单独   = 535 RPM（−24%）
通道 + 工作量         → MTP+PDMux = 852 RPM（+20%）
```

### 对「空隙」说法的修正

先前把机制描述为「PDMux 把 prefill 藏进 decode 的空隙」。trace 显示这个说法不准确：

- base 的 GPU 忙占比已达 94.4%，**时间轴上几乎没有空闲**；
- 真正的差别不在「有没有空闲时间」，而在「同一段时间里能同时跑几个 kernel」。

所以 PDMux 的机制是：**让两条 stream 的 kernel 真正并发执行**，用计算密集的 kernel 填充访存受限 kernel 留下的 SM 空转，而不是利用时间轴上的空洞。

### 每步成本随 token 位数线性增长

base（无投机）在 12K 上改变并发的单步实测（`workload1000` 取前 400 条，命中 89.5%）：

| 并发（每步 token 位） | QPS | TPOT | 每位置成本 |
|---:|---:|---:|---:|
| 16 | 5.79 | 17.2 ms | 1.08 ms |
| 32 | 7.40 | 25.3 ms | 0.79 ms |
| 48 | 8.22 | 34.5 ms | 0.72 ms |
| 64 | 9.03 | 38.5 ms | 0.60 ms |
| 84 | 9.87 | 43.2 ms | 0.51 ms |

线性拟合：`TPOT ≈ 12.95 + 0.385 × batch`

两点重要含义：

1. **权重读取不是固定成本**。16 并发时 TPOT 仅 17.2 ms，远低于按「每步读满 34.19 GB 权重」估算的 26 ms。MoE 的专家覆盖随 batch 增长，权重读取量本身是 batch 的函数。
2. **外推到 MTP 的 verify 负载**：256 个 token 位 → `12.95 + 0.385 × 256 = 111.5 ms`，加上 3 次 draft 前向（约 45 ms）≈ **156 ms**，与实测的每步 156 ms 吻合。**MTP 变慢的主因就是每步 token 位从 64 变成 256，成本线性上涨**，不存在大块「无法解释的空转」。

### PDMux 释放的是 MTP 的投机能力

把三个配置换算到「每步 token 位数 / 每步耗时 / 单位成本 / 每秒产出」：

| 配置 | 每步位置数 | 每步耗时 | 每位置成本 | 每秒产出 token |
|---|---:|---:|---:|---:|
| base | 64 | 33.8 ms | 0.53 ms | 29.6 |
| MTP 单独 | 256 | 155.8 ms | 0.61 ms | **20.9** |
| **MTP + PDMux** | 256 | **73.1 ms** | **0.286 ms** | **44.6** |

MTP 的投机能力是「一步产出 3.26 个 token」，但代价是每步要处理 4 倍 token 位。单独使用时，4 倍成本吃掉了 3.26 倍产出，净亏。PDMux 把单位位置成本从 0.61 ms 压到 0.286 ms（−53%），3.26 倍产出才真正兑现，每秒产出达到 base 的 1.5 倍。

因此更准确的表述是：**PDMux 并不创造新的计算能力，它把 MTP 已经具备但被 4 倍位置成本抵消的投机收益释放出来。**

### 对照一：零 prefill 负载（PDMux 的收益是否来自「藏住 prefill 打断」）

构造：同一个 12K prompt 重复 1000 次，除第 1 条外全部命中（实测 99.7%），prefill 总工作量从 53 万 token 降到约 1.2 万。

| 组 | QPS | RPM | TTFT p50 | TPOT | 命中 |
|---|---:|---:|---:|---:|---:|
| MTP 单独 | 23.40 | 1,404 | 191 ms | 19.2 ms | 99.68% |
| MTP + PDMux | 26.31 | **1,579** | 300 ms | **16.3 ms** | 99.71% |

PDMux 仍有 **+12.5%**，收益没有消失，但显著缩小：

```
有 prefill（P=50）：  MTP 535  → +PDMux 852   = +59.3%（相对 MTP）
零 prefill：          MTP 1,404 → +PDMux 1,579 = +12.5%
```

**约 79% 的相对增益来自消除 prefill 对 decode 的打断；剩余 12.5% 机制未明。**

### 对照二：去掉 decode stream 的高优先级

临时把 `pdmux_context.py` 中两处 `torch.cuda.Stream(gpu_id, priority=-1)` 改为不带 priority，跑完即还原（已确认还原）。

| 场景 | 有优先级 | 无优先级 | 差异 |
|---|---:|---:|---|
| 零 prefill，RPM / TPOT | 1,579 / 16.3 ms | 1,495 / 17.2 ms | −5.3% / +5.5% |
| P=50，RPM / TPOT | 852 / 22.4 ms | 862 / 21.7 ms | +1.2% / −3.1% |
| P=50，TTFT p90 | 1,732 ms | 1,669 ms | −4% |
| 零 prefill，TTFT p90 | 407 ms | 418 ms | +3% |

两个场景方向不一致，差异均在噪声量级。**decode 高优先级对吞吐和 TTFT 都没有可辨识的影响。**

### TTFT 恶化的真正来源：prefill 被切片穿插

| 负载 | 每请求 prefill 量 | PDMux 带来的 TTFT p90 |
|---|---:|---:|
| 零 prefill（同一 prompt ×1000） | ~38 token | 407 ms（几乎无恶化） |
| P=50 | ~530 token | 1,669 ms（+1,296 ms） |
| 32K 真实 @64 并发 | ~2,789 token | 7,632 ms |

剂量关系明确：**prefill 越多，TTFT 惩罚越大。** `layer_split` 把 prefill 前向也切成 K 层一段并在段间插入 decode，首字必须等全部段跑完，因此 prefill 完成时间被拉长。

**结论：PDMux 用 prefill 的延迟换 decode 的连续性。这是同一机制的两个面，与优先级无关。** 因此 SLO 卡 TTFT 时调整优先级无效，只能减少 prefill 量（提高命中率）或关闭 PDMux。

### 局限

三份 trace 的时间窗口与请求量不完全对齐（MTP 单独那组因吞吐更低、耗时更长），因此适合做结构性对比（stream 数、并发比例、kernel 粒度），不宜直接换算成吞吐差值。

## 13d. TTFT 分解：p90 与 p95 由不同因素主导

全部数据来自 P=50 负载（12K、64 并发、chunk 固定 16384）。

### 分段粒度 K 只影响 p90

`K = split_forward_token_budget ÷ 实际 prefill 批大小`，再被 `split_forward_max_layers` 截断。模型共 40 层，故分段数 = ⌈40/K⌉，段边界（可被打断的点）= 分段数 − 1。

| K | budget | 分段数 | 段边界 | RPM | TTFT p50 | **p90** | p95 | TPOT |
|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 4 | 65,536 | 10 | 9 | 842 | 422 ms | **2,574 ms** | 13,765 ms | 21.3 ms |
| 8 | 131,072 | 5 | 4 | 852 | 429 ms | **1,761 ms** | 11,215 ms | 22.4 ms |
| 16 | 262,144 | 3 | 2 | **868** | 422 ms | **549 ms** | 10,774 ms | 22.6 ms |

**p90 与段边界数单调相关（9→4→2 对应 2,574→1,761→549 ms），吞吐同时略升（842→868）。** 机制：每个段边界都是一次把 GPU 让给 decode 的机会；多数请求能连续跑完所有段（p50 不受影响，422–429 ms），被多次插队的少数请求构成 p90。段边界越多，被多次打断的概率越大。K=16 在吞吐与尾部上都是净收益，无代价。

该解释由「段边界数 vs p90」的相关性推出，未直接测量段间等待时间。

### p95 由冷启动波次主导，与 K 无关

P=50 的 1000 条请求按轮转排列，前 100 条即 50 条 rep0 + 50 条 rep1，并发 64 时开跑的正是这两批，此时缓存为空。

| rep 批次 | 请求数 | 命中率 | TTFT 中位数 | 最大 |
|---|---:|---:|---:|---:|
| rep 0 | 50 | **19.0%** | **11,099 ms** | 22,251 ms |
| rep 1 | 50 | 97.9% | **12,667 ms** | 22,250 ms |
| rep 2 | 50 | 98.3% | 450 ms | 2,981 ms |
| rep 3+ | 850 | 99.7% | 463 ms | 519 ms |

TTFT > 5 s 的 83 条请求全部落在 rep0（39 条）与 rep1（44 条）。K 从 8 提到 16 时 p95 仅从 11,215 降到 10,774（−4%），因为 rep0 的耗时是「真算 9.6k token」本身，而非分段等待。

冷启动总量与量级吻合：

```
冷启动需真算的 prefill = 50 × 12,037 = 601,850 token
按 20k tok/s 折算 ≈ 30 s GPU 时间
观测最大 TTFT ≈ 22 s
```

决定性对照：同一 PDMux + MTP + 64 并发配置，换成「同一 prompt ×1000」（无冷启动）后，p95 为 **868 ms**，与 P=50 的 11,182 ms 相差 **13 倍**。

### rep0 的 19% 命中来自共享 system prompt

rep0 的 50 条请求中，47 条的 `cached_tokens` 精确等于 **2,432**，仅 3 条为 0（首批 prefill 早于该前缀入缓存）。2,432 ÷ 12,942（rep0 中位 prompt）= 18.8%，与实测 19.0% 一致。

这段 2,432 token 是所有轨迹共用的 OpenHands system prompt。它也解释了此前所有「缓存完全失效」场景为何都停在 ~20%：**那个 20% 地板就是 system prompt，不是缓存失效。**

### 报告口径

P=50 的 p95 = 11 s 是 1000 条请求的**冷启动瞬态**，不是稳态特性。若请求数增至 5000，这 100 条冷请求占比降到 2%，p95 会落到 ~450 ms 量级。对外报 p95 时必须注明「含冷启动」还是「稳态」，两者相差 13 倍。

## 14. 主要结论

1. **Mamba 槽决定并发上限**：`并发 = ⌊槽数 / S⌋`。128→25、160→32、336→64 三处吻合。
2. **Mamba 槽同时决定前缀缓存容量**：空余 = `槽数 − 并发 × S`。满载时 running 请求会吃光缓存槽，前缀缓存被静默关闭（命中率塌回 system prompt 的 ~20%）。这是本轮最重要的坑。
3. **PDMux 的本质是让两条 stream 的 kernel 真正并发执行**（trace 实测：并发内核时间 0.5% → 24.7%，见第 13c 节），而不是把工作塞进时间轴的空洞——base 的 GPU 忙占比本就有 94.4%。其收益约有 79% 来自消除 prefill 对 decode 的打断（零 prefill 对照：相对增益从 +59.3% 降至 +12.5%），decode 高优先级的贡献实测接近零（去掉后吞吐差异方向不一致、TTFT p90 仅差 4%）。
4. **PDMux 依赖投机**：无投机时 12K −13.4%、32K −5.3%、64K −3.5%，随上下文变长收敛到 0 但从不转正；有投机时 +20%（12K）/ +33%（32K）。同一条 PDMux 在 P=200 的 prefill 受限负载下是 −12%。
5. **SM 硬预留是纯损失**：分区不改善 TPOT，只削弱 prefill。用 `prefill_full_sm` 即可（流优先级实测无影响）。
6. **HiCache 只在工作集超出 GPU 容量时才有价值**：合成 P=200 负载下 16 GB 无效、64 GB 让命中率 20%→83.3%、QPS +163%；12K 真实负载工作集 820k < KV 池 990k 时，加 64 GB 也只提升 0.1 个百分点、QPS 反降 5.5%。
7. **HiCache 的写入策略是决定性变量**：32K + MTP 场景下，主机 32 GB 配默认 `write_through` 完全无效（58.8%），换 `write_back` 后命中率 58.8%→85.1%、吞吐 131→288 RPM（+120%），且超过无投机的 base（263 RPM，同命中率）。原因是 `write_through` 要求父节点先备份才备份子节点（`hiradix_cache.py:858`），长上下文高压下备份链从中间断开，主机中只剩无法构成前缀的碎片。
8. **MTP 在 32K 下单独使用是 −32%**（263→178 RPM，命中率 85.0%→68.6%）：draft KV 把池从 1.548M 压到 1.196M，低于 64 agent 的保留需求 1.19M。配 `write_back` 的 HiCache 后回到 85.0% / 275 RPM，再加 PDMux 到 288 RPM（+9.5%）。**32K 下 HiCache 对 MTP 是必需项，不是优化项。** 12K 下同配置 MTP 单独为 +3.3%，因为工作集 576k 装得进 990k 的池。
9. **MTP 单独在 64 并发下是负收益**（−24%），TPOT 33.8→47.8 ms；只有配合 PDMux 才转为正收益。该结论仅在高命中、decode 完全饱和时成立；真实 12K 负载下 MTP 单独为 +3.3%。
10. **长上下文放大 PDMux（配 MTP）的收益，也放大它的代价**：12K 时 +20.3% 吞吐，32K 时 +32.6%；TTFT p95 代价从 +104% 涨到 +1,613%。但 `base+pdmux` 在 32K/64K 仍为负，说明这份增量来自 MTP 而非长上下文本身。
11. **PDMux 的收益随并发单调下降**：32K 下 24 并发 +12.9%、32 并发 +9.5%、64 并发 −8.6%。并发升高后两条 lane 抢同一条 HBM 带宽，可并发的 kernel 各自更接近带宽上限，重叠增益被摊薄。base 的绝对吞吐在 64 并发最高（301 RPM），全功能配置在 32 并发到顶（288 RPM），两线在 32–64 间交叉。
12. **decode 成本对上下文几乎不敏感**：每并发请求吞吐 12K 23.6 → 32K 22.6 → 64K 21.5 tok/s，5 倍上下文只降 9%。MoE 模型下 attention 占比小，这是 PDMux 单独吃不到长上下文红利的原因。

13. **PDMux 释放的是 MTP 的投机能力，而非创造新算力**（第 13c 节）：MTP 每步处理 4 倍 token 位（64 → 256），单步成本随位置数线性增长（`TPOT ≈ 12.95 + 0.385×batch`），4 倍成本吃掉 3.26 倍产出，故单独使用为 −24%。PDMux 把单位位置成本从 0.61 ms 压到 0.286 ms，投机收益才兑现，每秒产出达 base 的 1.5 倍。trace 佐证：并发内核时间 base 3.4%、MTP 单独 0.5%、MTP+PDMux 24.7%。

## 15. 已知局限

- 输出长度固定 128 token（`ignore_eos`），真实分布中位数为 23、均值为 58，故 MTP 的收益在此被低估、TPOT 被高估；组间横向比较仍成立。
- 上下文测到 64K，但 64K 只在无投机下验证过（P=20、并发 20）。64K + MTP 需要把 P 降到约 18 以内，因为 draft KV 会吃掉 35 万 token 容量。
- 长上下文实验的并发随上下文下降（12K 用 64、32K 用 32、64K 用 20，均受 KV 限制），跨上下文长度的绝对吞吐不可直接比较，只有 PDMux 的相对增益可比。
- 32K 缺 `mtp` 单独一组，故 +33% 中"长上下文贡献多少、MTP 贡献多少"未能完全拆分；由 32K `base+pdmux` 为 −5% 可推知增量主要来自 MTP。
- 除第 13 节外，其余负载为合成的重复前缀形态，非真实 agent 并发到达。第 13 节的 64-agent 负载只跑了 MTP+PDMux 一组配置（含三档 HiCache），未跑 `base` 对照，故"真实负载下 PDMux 增益多少"仍未直接测得。
- P=50 的 852 RPM 是"工作集完全驻留 + decode 受限"的天花板，不能直接外推为生产值。第 13 节的真实负载实测 667 RPM，是其 78%。此前按命中率插值给出的 300–420 RPM 估计偏低，因为真实 agent 负载的工作集（820k）小于 KV 池，不存在合成 P=200 那种驱逐。

## 16. PDMux 的优势与代价（定稿）

### 一句话

**PDMux 释放的是 MTP 的投机能力。** MTP 一步产出 3.26 个 token，代价是每步要处理 4 倍 token 位（64 → 256）；单步成本随位置数线性增长，4 倍成本吃掉了 3.26 倍产出，所以 MTP 单独是 −24%。PDMux 把前向切成 K 层片段分到两条 stream 上交替执行，使 prefill 批次不再整段插入 decode 流，把单位位置成本从 0.61 ms 压到 0.286 ms（trace 实测并发内核时间 0.5% → 24.7%，见第 13c 节），投机收益才兑现——每秒产出达到 base 的 1.5 倍。**它不创造新算力，只让已有的投机能力变得划算。**

### 优势

**1. 吞吐：decode 受限时 +20% ~ +33%**

| 负载 | 命中率 | prefill/请求 | base | +MTP+PDMux | 增益 |
|---|---:|---:|---:|---:|---:|
| A（12K 合成） | 95.6% | 530 | 708 RPM | 852 RPM | +20.3% |
| B（12K 真实） | 83.5% | 1,425 | 553 RPM | 667 RPM | +20.6% |
| l32b（31.5K 高命中） | 97.1% | 914 | 340 RPM | 451 RPM | **+32.6%** |
| C（18.6K 真实） | 85.0% | 2,789 | 263 RPM | 288 RPM | +9.5% |

增益由 `prefill/请求` 决定，而非上下文长度：同样 32K、同样 32 并发，命中 97% 时 +32.6%，命中 85% 时 +9.5%。

**2. TPOT：decode 被隔离**

| 负载 | 对照 | +PDMux | 变化 |
|---|---:|---:|---:|
| A（12K） | 45.1 ms | 22.4 ms | −50% |
| l32b（31.5K 高命中） | 36.3 ms | 19.8 ms | −45% |
| C（18.6K，bs=32） | 49.2 ms | 39.1 ms | −21% |

**3. 它是 MTP 的前提而非加速器**：A 组 MTP 单独 −24%，MTP+PDMux +20%。不开 PDMux 时 MTP 在本机器上为纯亏损。

**4. 消除 base 的 TTFT 异常**：12K 2,286 → 236 ms；32K 2,438 → 517 ms。机制未查清（见第 15 节），但两个负载复现。

### 代价

**1. 不开投机时恒为负收益**

| 负载 | base | +PDMux | 变化 |
|---|---:|---:|---:|
| A（12K） | 708 RPM | 613 RPM | −13.4% |
| 32K 单轮 | 340 RPM | 322 RPM | −5.3% |
| 64K 单轮 | 201 RPM | 194 RPM | −3.5% |
| C（18.6K） | 263 RPM | 262 RPM | −0.4% |

四个负载、四个上下文长度无一为正，随上下文变长收敛到 0 但不转正；同期 TPOT 33.8→40.0 ms 变差。

**2. prefill 受限时吞吐倒贴**：P=200（命中 20%）152 → 134 RPM（−12%），但 TPOT 108.6 → 35.8 ms（−67%）——decode 被保护，代价由吞吐承担。

**3. TTFT 尾部**：12K p95 5,495 → 11,215 ms（+104%）；32K 高命中 p95 359 → 6,151 ms（+17 倍）。配 MTP + 64 并发时 p90 亦从 373 涨到 1,732 ms。根因是 prefill 前向被切成 K 层片段并在段间插入 decode，首字要等全部段完成——**代价随每请求 prefill 量线性增长**（第 13c 节剂量表），与流优先级无关。

p90 与 p95 的可调性不同（第 13d 节）：**p90 由分段粒度 K 决定，K 从 4→8→16 可使 p90 从 2,574 降到 549 ms，且吞吐不降**；**p95 由冷启动波次决定，K 几乎无效**（−4%），只能靠提高命中率或缩短冷启动量改善。

**4. 低并发下投机摊不薄**：32K 只能跑 32 并发时，MTP+PDMux 的 TPOT 39.1 ms 高于 base 的 36.6 ms，收益全在吞吐。

**5. 配置被锁死**：必须开 overlap schedule；与 prefill CP 互斥；只能 `layer_split` / `standard`；`sm_group_num` 必须 3。SM 硬分区无收益（psm120/78 的 TPOT 完全相同，只削弱 prefill）。

**6. 工程成熟度**：非上游功能，本分支为跑通改了 3 处（校验钩子放宽、`FutureMap.stash` 设备迁移、decode lane 的 Mamba 状态提交）。

### 收益的量化模型

```
PDMux 收益 ≈ (可并发的 kernel 时间占比) × (单个 kernel 内部的 SM 空转率) − (切分与同步开销)
```

- 可并发时间越多 → 收益越大（trace：0.5% → 24.7%）
- 单个 kernel 内部空转越多（访存受限越严重）→ 填充越有价值 → 收益越大
- 切分与同步是每步的固定开销；步骤越短（batch 小、无投机）时它占比越高，因而转为负收益

l32b 同时满足这两条（32K 长上下文 + 97% 命中），因此 +32.6% 为全部实验最高。C 组两条都较差，仅 +9.5%。

### 决策规则

```
开 PDMux  ⟺  投机解码已开  ∧  prefill/请求足够小  ∧  SLO 不卡 TTFT p90
```

配套前提（均踩过坑）：

```
① max-mamba-cache-size ≥ 并发 × S + 要缓存的前缀条数
② MTP 使工作集超出 GPU KV 池时，必须开 HiCache 且 --hicache-write-policy write_back
```

### 推荐配置

| 场景 | 配置 | 结果 |
|---|---|---|
| 12K、高复用 | `MTP+PDMux`（budget 262144） | **868 RPM / TPOT 22.6 ms / TTFT p90 549 ms** |
| 12K、真实 agent | `MTP+PDMux` | 667 RPM / TPOT 34.9 ms |
| **长上下文 + 高命中（长文档批量处理）** | `MTP+PDMux` | **451 RPM / TPOT 19.8 ms（最佳场景）** |
| 长上下文 + 低命中（多 agent） | `MTP+PDMux+HiCache(write_back)` | 288 RPM，TPOT 让位于 base |
| 不开投机 | 不要用 PDMux | 一律为负 |

### 三个被推翻的早期判断

| 早期结论 | 修正 |
|---|---|
| PDMux 是通用 prefill/decode 重叠 | 无投机时恒为负；它重叠的主要是投机产生的工作 |
| 长上下文放大 PDMux 收益（推演） | 前提是命中率跟得上；低命中时长上下文反成负担 |
| HiCache 无效，生产别开 | 默认 `write_through` 在长上下文失效；`write_back` 下命中率 60.2% → 85.1% |

### C3. SLO 约束下的容量（TTFT p90 ≤ 5 s，TPOT ≤ 40 ms）

| | 最大 QPS | 并发 | 瓶颈 |
|---|---:|---:|---|
| base | 4.39 | 32 | TPOT 36.6/40（裕度 9%） |
| MTP+PDMux+HiCache(wb) | **4.79** | 32 | TPOT 39.1/40（裕度 2%） |

64 并发全部不合格（base TPOT 65.1、全功能组 TTFT p90 8,945）。放宽到 p90 ≤ 9 s / TPOT ≤ 50 ms 后最大值不变——瓶颈始终是 TPOT，不是 TTFT。

### C4. KV dtype 与带宽拆解（64 并发，32K）

| 组 | bf16 KV TPOT | fp8 KV TPOT | 变化 | bf16 RPM | fp8 RPM |
|---|---:|---:|---:|---:|---:|
| base | 65.1 ms | 58.2 ms | −10.6% | 301 | 324 |
| MTP+PDMux+HC(wb) | 49.8 ms | 40.4 ms | −18.9% | 275 | 318 |

按 `TPOT = fixed + k` 解方程，KV 读取占每步的比例：base 21%（13.8 ms），投机路径 38%（18.8 ms）。

实测显存读带宽 1,315 GB/s（拷贝 1,278 GB/s），显存频率 12,481 MHz。据此 base 每步访存：权重 34.19 GB ≈ 26 ms、KV 22.7 GB ≈ 17 ms，合计约 43 ms / 65.1 ms（67%）。**decode 是访存受限，其中权重是大头（40%），KV 次之（27%）。**

### 结论矩阵：各特性的符号随负载变化

| 特性 | 12K 合成 | 12K 真实 | 32K 真实 | 决定性条件 |
|---|---:|---:|---:|---|
| MTP | −24% | +3.3% | +4.6%¹ | 缓存是否被 draft KV 压穿 |
| PDMux | −13%（无投机）<br>+20%（有投机） | +20.6%（有投机） | −0.4%（无投机）<br>+4.7%（有投机） | 是否开投机 |
| HiCache | −1.5% | −4.7% | +9.5%² | 工作集是否超出 GPU 池 + 写入策略 |

¹ 32K 下 MTP 必须配 `write_back` 的 HiCache，否则 −46%。
² 32K 下 HiCache 必须用 `write_back`，默认 `write_through` 为 −50%。

### 三表合并的观察

1. **PDMux 的符号只取决于是否开投机**：有投机时 +4.7%~+20.6%，无投机时 −13%~−0.4%。三张表一致。
2. **HiCache 的符号只取决于容量与写入策略**：工作集装得下时是纯开销；装不下时是必需品，但只在 `write_back` 下有效。
3. **TPOT 与 TTFT 反向**：吞吐最优的组 TPOT 最好（22.4 / 34.9 ms）但 TTFT 最差（429 / 1,523 ms）；`base+PDMux` 的 TTFT 最好（236 / 517 ms）但 TPOT 最差（40.0 / 51.8 ms）。
4. **最优配置随负载变化**：12K 合成是 `MTP+PDMux`（852 RPM）；12K 真实是 `MTP+PDMux`（667 RPM）；32K 真实是 `MTP+PDMux+HiCache(write_back)`（288 RPM）。
